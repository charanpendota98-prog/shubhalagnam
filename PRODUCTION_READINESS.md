## Improvements now present in the repository

- `docker-compose.prod.yml` is standalone and must not be layered over the development Compose file. It uses one backend worker, keeps the API off the host network, binds the frontend to host loopback for Caddy, and maps runtime JSON/state/media paths into a named volume.
- The backend refuses production startup if durable paths are absent, outside the configured persistent root, or unwritable; it also rejects missing, unreadable, corrupt, structurally incomplete, unmarked-empty, malformed, or duplicate-profile core database state before restoring profiles or starting workers. A populated legacy core database is accepted after validation. A clean empty database can be initialized only with the separate one-shot `bootstrap_core_db.py` operator command: `--confirm-new-install` for an absent path, or after verified backup `--confirm-existing-empty` for a structurally valid legacy empty file. The tool checks the durable-volume path, preserves metadata in the legacy-empty case, and refuses any database containing records. Normal server startup has no empty-database override. Corrupt or incomplete source files are never overwritten by the gate. Startup blocks rather than silently starting with no registrations.
- Public registration makes a forced durable checkpoint before returning success; routine autosave debouncing can no longer be the only copy of a newly accepted profile. Core JSON writes now use a unique private temporary file, file fsync, atomic replacement, POSIX `0600` permissions, and serialized writers. These are local code-path protections, not a guarantee against disk/host failure or an unverified production volume.
- Production also rejects auth bypass and test payment fixtures and requires owner/worker configuration and a real OTP provider. Per-user token-revocation counters must use `TSAP_TOKEN_VERSIONS_FILE` inside the configured durable state directory so backups include them; unreadable/corrupt state fails closed, and revocation writes are atomic and private.
- PostgreSQL and Redis were removed from the production stack because the application is not migrated to use them. The current system of record remains a single-process JSON store; horizontal scaling/high availability are not supported.
- The backup utility reads/restores the configured core database and satellite JSON/JSONL files from the durable state path, including token-revocation counters. Restore rejects malformed metadata, duplicate entries, incomplete core collections, malformed/duplicate profile identities, unmarked empty stores, and archives over its decompressed-size/entry limits before changing state. Any reduction in active core record counts (including registrations or payments) is refused with HTTP 409 until the authorized owner explicitly confirms; a private same-volume pre-restore snapshot is created before writes, satellite files are installed before the core DB, and a missing configured core DB is never exported as an empty placeholder. Automatic same-volume snapshots use atomic writes and private POSIX modes (`0700` directory / `0600` archive); they are still not an off-site backup. The owner-page and backup guide state that the app ZIP does **not** include uploaded media, secrets, or the Docker volume.
- Docker build contexts exclude local secrets, runtime stores, media directories, synthetic fixtures, tests, virtualenvs, and frontend build caches.
- Jathakam uploads and profile media use the configured media root. Registration requires a technically valid image; new photos stay private/pending suitability review, and approval is not represented as identity verification or proof that the applicant is pictured. Public visibility remains opt-in and approval/privacy-state gated. The production updater no longer switches branches/remotes, backs up plaintext `.env`, restores application data, or removes Compose orphans automatically; deployment is pinned to a reviewed commit and an operator backup acknowledgement.
- Old payment/deployment notes that contained guessed recipients, obsolete Compose instructions, or unsupported readiness claims are now archived or replaced with explicit safety guidance.
- Public support, operator/legal identity, location, and grievance contacts now default to absent and are injected only from explicit deployment configuration. Legal pages hide empty fields; JSON-LD omits an empty email, unsupported Hyderabad/area-served assertions and the fabricated legal-name default were removed. The unverified legal-acceptance API is retired (410) and its owner-summary object is removed. Web-push readiness requires the optional sender package, a valid matching VAPID key pair, and an owner-configured subject; no contact fallback is synthesized. Visitor analytics now use a process-local HMAC pseudonym, minimized page/referrer/campaign fields, a 30-day maximum and 10,000-event cap, and a response that exposes neither visitor IDs nor totals; the privacy notice distinguishes this from separate infrastructure/provider logs.

## Remaining production blockers

1. **Existing data and migration are unknown.** Determine whether the current host has real profiles, payments, referrals, photos, cards, voice files, jathakam uploads, token-revocation counters, or other state. The new core-DB gate blocks a missing/empty replacement database, but cannot discover, copy, or verify an external live database; no production host or volume was inspected. Preserve any existing `token_versions.json` values into the new `TSAP_TOKEN_VERSIONS_FILE` before cutover; do not silently start with an empty counter if prior revocations may exist. Map every existing store/media file to the same named volume and compare it with off-host backups before changing the live deployment. A fresh named volume is empty; never let it silently replace an existing source of truth.
2. **Disaster recovery is incomplete.** The in-app ZIP is a sensitive JSON/JSONL export, not a full backup. Configure encrypted off-host backups of the complete data volume, including uploaded media, and test a restore to a disposable environment. Local startup snapshots on the same volume are not disaster recovery.
3. **Production infrastructure is unverified.** No authorized host, verified DNS/domain, TLS proxy, secret manager, deployment pipeline, monitoring, or release approval is connected to this session. Run Compose interpolation/build/health/restart checks on a staging host before release.
4. **Provider configuration is owner-controlled and absent here.** Production needs real SMS or an owner-controlled OTP bridge, correctly provisioned owner/worker accounts, and—if charging is enabled—merchant credentials and sandbox-verified signature, amount/currency, duplicate/replay, refund, and reconciliation behavior. No business contact, merchant recipient, secret, payment reference, or channel destination is invented here. Keep live payments and outbound publishing off until operator sign-off.
5. **Storage is single-node/file-based.** Continue with one backend worker only. Before horizontal scaling or high availability, migrate the system of record to a transactional database and redesign/test concurrency, sessions, rate limits, and background jobs.
6. **Release QA remains incomplete.** The latest remote PR gate installed Chromium and passed responsive checks across the configured viewports/routes plus rendered axe and keyboard-focus checks. Local browser execution is still unavailable in this sandbox, and those CI checks do not replace real-device mobile/desktop review, browser compatibility, performance/load, staging-provider, privacy/retention, incident, rollback, and media-restore drills.
7. **The worktree is not a reviewed release.** Review the full change set, run the final checks, merge through the authorized process, and deploy only the reviewed commit. Do not deploy this mutable worktree.
8. **Historical credential exposure needs owner action.** A session-token-like value, phone number, and password hash exist in the base commit's security-audit evidence. The current file copy is redacted, but this work did not rewrite Git history or verify whether the historical account remains active. Treat related credentials as potentially exposed; the owner should rotate affected credentials, verify/revoke sessions using the durable token-version file on the actual production volume, and decide on authorized history cleanup before release.
