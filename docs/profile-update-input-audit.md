# Profile update input and rendering audit

Scope: six omitted text fields and the unvalidated boolean field in `/api/profile/update`, plus views and exports that can display member-supplied profile text. Audited against PR211's merged tree with this patch. No production records were read or changed for the audit.

## Input boundary

- `birth_time` (30), `weight` (20), `brothers` (20), `sisters` (20), `exp_age_min` (3), `exp_age_max` (3) now use the existing `clean()` path and the same limits as registration. Registration's later weight re-clean now also uses 20 instead of 12, matching its initial validation and the update path.
- `is_nri` is a boolean, not free text. It now uses the existing strict boolean parser before shared-record mutation. False-like supported values remain false. Unsupported strings, objects and arrays return localized 400 responses without partial mutation.
- Null and omitted values still mean no change. Existing records are not rewritten. Authentication, checkpoint rollback, privacy handling and public serialization are unchanged.
- An AST coverage assertion compares every writable field to either the free-text map or an explicit specialized normalizer. The endpoint tests separately exercise each new field, owner rejection, invalid-boolean atomicity and failed-checkpoint rollback.
- This patch does not impose new age/count/time formats. Those fields historically accept optional descriptive text; semantic validation is a separate product change.

## Rendering paths

- `frontend/src/app/(telugu)/admin/` and `control/`: no raw HTML assignment or `dangerouslySetInnerHTML` sink found. Profile values are JSX children/attributes. English routes reuse the corresponding views.
- Account editor and profile view: normal member values are JSX text or controlled input values. React escapes them. `is_nri` is used as a badge condition, not inserted as HTML.
- `search/[id]/ProfileView.tsx`: its print document is a manual HTML sink. Existing `escapeHtml()` covers each profile interpolation, including nested family/location text and unknown diet/profile-for labels. New EN/TE browser tests inject hostile values into fields actually printed (such as height and education), verify the view stays inert, capture the real print document, and assert no injected image, handler or script nodes exist. The six newly sanitized text fields are not rendered by ProfileView or its print document, so these tests do not prove their output escaping. Their input handling is covered by backend tests. The is_nri field is only a badge condition. The sole script is the fixed print-on-load script.
- The same profile view's contact SVG sink is generated by `contactQrSvg`, not from these profile fields. This audit does not widen contact access or probe production tokens.
- Profile page JSON-LD and member-story JSON-LD use `serializeJsonLd`, which replaces `<`, `>` and `&` with JSON escapes. Other raw HTML insertions found in the frontend are static SEO data, not these profile fields.
- `backend/card_pro.py` draws member values as Pillow text into raster images. `card_generator.py` delegates to it. These are not HTML sinks.

No executable rendering sink for these six text fields and boolean field was confirmed. The stored-input gap is still a real defense-in-depth defect and is fixed independently of current escaping. Historical malformed values are not backfilled by this release.

## Bounds

This is a focused audit, not a claim that every unrelated route, SVG generator, PDF component or third-party library is free of injection bugs. Broader data/auth/payment review follows separately. No schema, religion policy, rewards, paid-checkout mode or dependency change is included.


## Nonblank-to-empty update protection (PR224)

Profile updates prepare cleaned free-text values locally before any shared-record assignment. A nonblank submitted value that the existing cleaner erases entirely returns a curated English and romanized Telugu 400 response. The whole update is rejected, with no partial or temporary record writes, persistence or card generation. Explicit empty/whitespace strings remain the clear operation; null/omitted optional text remains no-op. Required location validation is unchanged: an explicit null district is still rejected before cleaning. Readable text inside ordinary formatting tags still follows the existing cleaner. Limits, global clean(), registration semantics and code-point truncation remain unchanged. No historical record rewrite occurs.

Tests cover the six previously omitted fields plus name/about/country, markup/control/protocol-only values, both payload orders, exact no-echo locale errors, deliberate clearing, null, readable Telugu/formatting, and checkpoint rollback. Grapheme-safe caps remain a separate design task, not part of this change. The current cleaner removes individual tags, not entire script contents; output escaping remains required.

The profile-update error formatter has one endpoint caller. It now preserves detail only for exact server-owned known literals; dynamic or unknown detail is replaced with curated English text, so submitted choices cannot leak through the legacy detail field. Status and exception headers are preserved. Exact-wire frontend fixtures are refreshed deliberately. This does not change shared validators or errors on other endpoints.
